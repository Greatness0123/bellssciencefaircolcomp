
SENTINEL AI
Security Operations DashboardInterface & User Experience Brief
Design handoff document for the product designer
Purpose
Product direction
Define the screens, information hierarchy, interactions and user journeys for security personnel using Sentinel AI.
A modern Security Operations Centre (SOC)-style workspace to monitor the agent, investigate alerts, understand network activity and coordinate safe responses.

1. Product vision
The Sentinel AI dashboard is the command interface for authorised cybersecurity personnel. It should help an analyst understand what is happening across the monitored network, identify suspicious activity, investigate the evidence behind an alert, and record or initiate an appropriate response.
This is more than a notification page. It connects three things: alerts generated by the security agent, visibility into monitored network assets and locations, and the decisions/actions taken by security personnel.
Visual direction: professional, calm and information-rich. Use a dark SOC-inspired theme, readable tables and charts, clear severity indicators, and a consistent navigation system.

Role
Responsibilities

Monitors alerts, investigates activity, assigns alerts and documents findings.
View alerts/assets; acknowledge, assign, update status and add notes.
Incident Responder
Coordinates approved containment and recovery actions.

For the MVP, roles can be simplified to Administrator, Analyst and Viewer. Design the permission model so additional roles can be introduced later.
3. Main application layout and navigation
Use a persistent left sidebar, top bar and central content area. The top bar should contain workspace/organisation name, global search, notifications, help, user profile and sign out. An optional right-side context panel can show quick details for a selected alert or asset.

4. Registering authorised profiles
Access should be controlled. Do not design an unrestricted public sign-up page. The recommended approach is administrator-controlled invitations or account creation.
4.1 User management page
Table of authorised personnel: name, email, role, account status, date added and last sign-in.
Primary action: “Add authorised user” / “Invite user”.
Search and filters by role, active/inactive status and pending invitations.
Row actions: view profile, edit role, deactivate account, resend invitation and revoke access.
Require confirmation before deactivation or permission changes.
4.2 Add / invite user form
Field
Expected behaviour
Full name
Required.
Work email
Required; validate format and prevent duplicate accounts.
Role
Dropdown of available roles.
Permission summary
Briefly explain what the selected role can and cannot do.
Invitation
Send a time-limited invitation; show Pending until accepted.

After invitation, show a confirmation state and the account as “Invitation pending”. Once accepted and credentials are set, show “Active”. Administrators must never see users’ passwords or recovery codes.
4.3 Account activation flow
User opens a secure, time-limited invitation link.
User confirms identity and sets a password.
User configures multi-factor authentication if enabled.
User accepts the organisation's access notice.
Account becomes Active and the administrator can see the updated status.
5. Sign-in and account security screens
5.1 Sign-in page
Sentinel AI logo and the label “Security Operations Console”.
Email/username and password fields, with show/hide password control.
Primary “Sign in” button and “Forgot password?” link.
Optional remember-device control only if permitted by security policy.
Notice: “Authorised personnel only. Activity may be logged.”
No public Create Account link when access is invitation-only.

7. Alerts page
This is the main operational queue. Analysts should be able to prioritise work without opening every alert.
Column
Meaning

Severity
Critical, High, Medium, Low or Informational.
Alert title
Short descriptive name, e.g. “Repeated failed login attempts”.
Category
Port scan, suspicious connection, authentication anomaly, unusual data transfer, etc.
Affected asset
Hostname or asset name, e.g. AI-App-Server.
Network location
Network segment, VLAN, subnet or monitored zone, if known.

Search by title, asset, IP, alert ID or category.
Filter by severity, status, date/time, network segment, asset, category and assigned analyst.
Sort by newest, oldest, highest severity or recently updated.

Bulk actions should be limited to safe workflow operations such as assigning or acknowledging.

8. Alert details and investigation
Selecting an alert should open a full detail page or substantial side panel. This is where the analyst understands what was detected and decides what to do.
8.1 Alert header
Alert ID and descriptive title.
Severity and current workflow status.
First detected and most recently observed timestamps.
Affected asset and network location.
Assigned analyst and an “Assign to me” action.
8.2 Required information blocks
Block
What to show
What happened
Plain-language explanation of the suspicious activity.
Why it was flagged
Detection rule/behaviour that triggered the alert, such as a connection threshold.
When
First seen, last seen, event time and alert creation time.
Where
Sensor name, network segment/VLAN/subnet, affected hostname and interface when known.
Source / destination
IP, port, protocol and traffic direction where available.
Evidence
Relevant event/log excerpts, counts, metadata, rule ID and supporting observations.
Impact / scope
Potentially affected monitored assets; do not claim compromise without evidence.
Recommended next steps
Investigation checklist, clearly labelled as guidance.
Related alerts
Other events involving the same source, destination, asset or time window.

8.3 Timeline and analyst actions
Show a chronological timeline of first observation, repeated activity, detection, acknowledgement, assignment, notes and response actions. Every entry should show actor/system, timestamp and action.
Action
Behaviour
Acknowledge
Confirms an analyst has seen the alert; does not mean it is resolved.
Assign
Assigns the alert to an authorised analyst.
Change status
Moves the alert through the workflow; request a reason where appropriate.
Add note
Adds a timestamped investigation note.
Escalate / create incident
Groups this alert with related alerts into a case.
Mark false positive
Requires a reason and preserves the decision in history.
Resolve
Requires resolution notes and a summary of what was done.

For the MVP, these may update stored records. Never show a response as successfully blocking traffic unless a real control integration executed and confirmed it.
9. Response and incident handling
The dashboard should help personnel respond, but distinguish recommendations, analyst decisions and actions actually executed. Early versions should favour human approval over automatic blocking.
Show recommended response steps based on alert category.
Allow analysts to record chosen action, reason, owner and outcome.
For future network-control integrations, show target, exact action and expected impact before confirmation.
Show execution state: Not started, Pending approval, In progress, Succeeded or Failed.
Record who approved and initiated the action, timestamp and result.
Alert type
Example analyst workflow
Port scan
Validate source/target; check if authorised testing; inspect related connections; escalate if unexplained.
Repeated failed logins
Check account and source context; verify legitimate activity; follow account-security procedures.
Suspicious outbound traffic
Review destination, volume, timing and application logs; determine whether expected.
Restricted endpoint access
Verify policy and identity; review backend logs and related requests.
Sensor failure
Treat as a visibility issue and restore monitoring; do not interpret missing telemetry as no threat.

Use careful language such as “suspicious activity detected”, “possible threat” and “requires investigation”. An alert by itself does not prove a successful intrusion.
10. Network Map
Show router/firewall, managed switch, AI application server, database, test client and security sensor.
Group assets by network segment, VLAN or security zone.
Use states: Online, Offline, Degraded and Unknown.
Show which sensor observes each segment and whether visibility is Confirmed, Partial or Unavailable.
Selecting an asset opens hostname, IP, role, status, last seen and recent alerts.
Selecting a link can show a traffic relationship if that data is available.
Do not imply full packet visibility just because a topology line is drawn. The sensor must actually receive the traffic, for example through correctly configured switch port mirroring or another approved collection method.
11. Agent Activity and health
This page tracks the security agent itself. Analysts must be able to distinguish a quiet network from a sensor that has stopped collecting data.
Panel
Information
Sensor status
Online/offline/degraded, sensor name/host, uptime and last heartbeat.
Event ingestion
Events received over time, last event timestamp, ingestion errors or dropped events if available.
Detection engine
Running/stopped, ruleset/configuration version, last update and processing errors.
Coverage
Monitored interfaces/segments and confirmed, partial or missing visibility.
System resources
CPU, memory and disk usage if collected.
Agent event log
Sensor start/stop, configuration changes, rule updates and pipeline errors.

Make stale data, disconnected sensors and failed ingestion highly visible. Show “Last data received” prominently.
12. Incidents / Cases
An incident groups related alerts into one investigation.
List: incident ID, title, severity, status, linked alert count, owner and last update.
Detail: summary, linked alerts, affected assets, timeline, notes and response record.
Suggested statuses: Open, Investigating, Containment, Monitoring, Resolved, Closed.
Preserve history when alerts are linked or unlinked.
Keep an individual detection alert distinct from an incident that analysts are managing.
13. Reports and analytics
Alert volume by day/week and severity.
Most common detection categories.
Most frequently affected assets and network segments.
Time to acknowledge and resolve, if timestamps support the calculation.
False-positive metrics only when enough labelled outcomes exist.
Agent uptime, event volume and sensor coverage.
Export with selected time range, generation time and data scope.
Never present placeholder numbers as real performance results. Label sample or demo data clearly.
14. Notifications
In-app notifications for new Critical/High alerts, assignments, escalations and agent-health failures.
Each notification links to the relevant alert, incident or sensor page.
Allow preferences for notification categories and sound/browser notifications.
Group repeated events where possible to reduce alert fatigue.
In-app notifications are sufficient for the MVP; email/SMS can be later enhancements.
15. Audit trail
Actions in a security operations tool must be attributable. Provide an audit trail visible to authorised administrators/auditors.
Record sign-ins, failed sign-ins, account changes and role changes.
Record alert acknowledgement, assignment, status changes, notes, false-positive decisions and resolution.
Record response approvals and execution results.
Each entry includes actor, action, timestamp, target object and outcome.
Ordinary users must not be able to edit or delete historical audit entries.

Recommendation

Keep the visual style professional and calm. Avoid excessive animation, glowing effects or decorative “hacker movie” styling that harms readability.
17. Empty, loading and error states
No alerts: “No alerts match these filters” with Reset Filters. Do not say “Your network is safe”.
No assets: explain that monitored assets/sensors have not been configured.
Sensor offline: prominent visibility warning; missing telemetry is not proof of no threats.
Stale events: show last received timestamp and elapsed time.
Loading: skeleton cards/rows while preserving layout.
Failed request: retry action and concise, non-sensitive explanation.
Permission denied: explain that this user cannot access the function.
No related alerts: state that none were found in the selected time range.
18. Key user journeys
A. Administrator invites an analyst
Administrator signs in.
Opens User Management and selects Add Authorised User.
Enters details and selects Analyst role.
Reviews permission summary and sends invitation.
Analyst activates account, sets credentials and configures MFA if enabled.
Administrator sees account status become Active.
B. Analyst investigates an alert
Analyst signs in and lands on Security Overview.
Dashboard highlights a new High-severity alert.
Analyst opens Alerts and filters to New / High.
Opens the alert and reviews description, time, location, source/destination and evidence.
Acknowledges and assigns the alert.
Checks related alerts and network asset context.
Records findings, follows response guidance and escalates if needed.
Resolves with notes after verification; actions appear in timeline/audit trail.
C. Analyst checks agent health
Opens Agent Activity.
Checks sensor status, heartbeat, last event and ingestion metrics.
If offline or stale, treats it as a monitoring issue and follows recovery process.
Confirms heartbeat and incoming events resume.

22. Design principles to preserve
Accuracy over appearance: only show network locations, evidence and sensor coverage the agent can actually collect.
Human-in-the-loop response: analysts review and approve consequential actions.
Separation of concepts: detection alert, analyst assessment, incident and executed response are different.
Traceability: meaningful actions are timestamped and attributable.
Explainability: show why an event was flagged and the supporting evidence.
Operational awareness: expose sensor health and telemetry freshness so blind spots are visible.
Progressive detail: keep overview scannable and reveal technical evidence on the alert detail screen.
